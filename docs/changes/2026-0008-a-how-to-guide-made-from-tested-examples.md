**Status:** shipped in v0.6.7

**Decisions:** D1 settled: keep EXAMPLES.md. D2 settled: a scalar test
first, its general part to docref when grammar follows. D3 settled: the
phrasebook stays separate, linked both ways. D4 settled: grammar
follows in its own session.

**Origin:** roadmap 2026-0008, from Iain's wish on 2026-11-09 for a much

## Decisions

- [x] **D1.** Should the guide absorb `docs/EXAMPLES.md`, so that it
  can be retired? No, not for now, Iain agreed on 2026-11-09. The two
  answer different questions: the guide "how do I do this task?", the
  examples "what does this one function do?". A guide covering all 302
  examples would stop being a guide, and one covering only the useful
  ones would lose the promise that every function is shown. The
  examples are also Go's own documentation, shown under each function
  on pkg.go.dev, and EXAMPLES.md is their copy for reading offline.
  Whether it's still needed can be asked again once the guide is
  written, as a decision of its own.
- [x] **D2.** Should the guide be generated by docref, shared in
  lock-step with grammar, or by a test of scalar's own? A test of
  scalar's own first, Iain agreed on 2026-11-09, as it makes the
  testing count for more. The work has two parts: splicing an
  example's body and output into Markdown between markers, which is
  general and is what docref already does for EXAMPLES.md; and the
  guide's own checks (every recipe from an example, the plain Go beside
  it, links to the examples and the phrasebook), which are scalar's
  alone. Both are built and proved in scalar first, without lock-step
  changes while the guide's needs are still being learnt. When
  grammar's session takes up D4, the general part moves into docref,
  identical in both, and the guide's checks stay here.
- [x] **D3.** How should the guide relate to `docs/PERL.md`? It stays
  separate, linked both ways, Iain agreed on 2026-11-09. The phrasebook
  is for someone who thinks in Perl; the guide is for a Go programmer
  with messy data, who may never have used Perl, and merging them would
  make Perl a step on the way into scalar. A phrasebook row is one
  idiom, and a recipe joins several steps into a task, so neither
  breaks cleanly into the other. Their tests differ too: rows are run
  in Perl, and recipes against their own output. Where they overlap, in
  the plain Go, each recipe links the rows for the idioms it uses, and
  the link check keeps those links whole. If writing the chapters shows
  that most recipes are rows strung together, the phrasebook could
  become an appendix to the guide; that would be a decision of its own.
- [x] **D4.** Should grammar's how-to guide follow? Yes, Iain said on
  2026-11-09, taken up in grammar's own session. When it is, the
  general part of D2 moves into docref.

## The plan

**Serves:** learning

**Size:** M (3)

**What:** generate each recipe in the [how-to guide](../HOWTO.md), its
code and the output it prints, from its `Example_` function, as
`docs/EXAMPLES.md` is generated, with a test of scalar's own that fails
when the guide and the examples differ. The same test checks the guide:
every recipe's code comes from an example, has the plain Go beside it,
and links to the [examples](../EXAMPLES.md) of the functions it uses
and the [phrasebook](../PERL.md) rows of the idioms it uses. The quick
start and the seven recipes there now move over first.

**Why:** the recipes are runnable examples already, but the guide is
copied from them by hand, so nothing notices when the two drift apart.
A guide that `go test` checks can grow to cover far more without going
stale, and is the ground for 2026-0010 and 2026-0011.

**Steps:**

1. A test of scalar's own, `TestHowTo` in `howto_test.go`, run with
   `-update` to rewrite the guide. In `docs/HOWTO.md`, each recipe's
   generated part sits between `<!-- recipe:name -->` and
   `<!-- /recipe -->`, made from `Example_name` and its plain Go twin,
   `Example_namePlainGo`, in `example_howto_test.go`:
   - the scalar code: the example's body, after any package-level
     declarations of that file it refers to, such as a pattern
     compiled once, so a reader sees all the code that runs;
   - what it prints, from its `// Output:`;
   - the plain Go twin's code, the same way;
   - a **Uses:** line linking each scalar function and method the
     recipe calls to its entry in the examples, found by type-checking
     the file, so `HV.Get` and `AV.Get` link apart.

   It fails when a region isn't what the examples generate, when a
   region has no example or an example in the file has no region, when
   a recipe has no plain Go twin, and when the twins print different
   output: the plain Go must do the same job, which keeps the
   comparison honest.
2. `TestDocLinksResolve`: every relative link in the documents
   resolves, `#anchor`s included, with anchors made from headings as
   GitHub makes them. It covers the guide's hand-written phrasebook
   links, and every other document too, which the practice asks for
   and nothing yet checks.
3. Move the seven recipes from `example_test.go` into
   `example_howto_test.go`, with the quick start as an eighth, each
   with the data it reads, and write each one's plain Go twin.
4. Put the markers into the guide, generate it, and fit the prose
   around the generated parts so the guide reads as it did. "Compared
   with plain Go" keeps its argument, pointing at the twins rather than
   code of its own that nothing runs. Link each recipe to the
   phrasebook rows for the Perl idioms it uses.
5. Show each failure the test promises with a planted case run on
   files in a temporary directory: a recipe edited in the guide alone,
   a missing twin, twins that print differently, and a broken link.
6. A CHANGELOG line, the record finished, and the guide's PDF read.

**Done when** the guide's code and output are generated, `go test`
fails on a recipe edited in the guide alone, on one without its plain
Go, and on a link that doesn't resolve, and the guide reads as it did.

## What happened

- **Outcome:** done as planned. `TestHowTo`, in `howto_test.go`,
  generates the quick start and the seven recipes, each between
  `<!-- recipe:name -->` markers, from `example_howto_test.go`: the
  scalar code, what it prints, the plain Go twin and a **Uses:** line
  linking each scalar function and method called to its example.
  `TestHowToCatches` plants each failure it promises: a recipe with no
  example, an example with no recipe, a missing twin, twins that print
  differently, and a recipe edited in the guide alone; the last was
  also tried on the real guide. `TestDocLinksResolve` checks every
  relative link and `#anchor` in the documents, the records included,
  and `TestDocLinksResolveCatches` plants a broken one of each kind.
  Nothing was broken when it first ran.
- **The twins:** eight, each the plain Go a Go programmer would write.
  Where the shape is known, a struct (the quick start, building
  records); where a missing field must be told from a null one,
  `map[string]any` with its type assertions (reading one event). Case
  folding uses `golang.org/x/text/cases`, as `strings.ToLower` isn't
  Perl's `fc`; a pattern with lookbehind is rewritten for Go's
  `regexp`. That every twin prints what its recipe prints is what keeps
  the comparison honest. The guide now recommends the plain Go where the
  shape is known, as the project's rules ask.
- **Changes from the plan:**
  - The Uses links come from type-checking the examples with
    `go/types` and the source importer, about a second per run; that
    tells `HV.Get` from `AV.Get`. They're ordered by where each name is
    written, as the walk finds a chain's outer call first.
  - A line ending `// test only` is left out of the guide, for the one
    recipe that changes `scalar.DefaultEngine` and must put it back so
    other tests don't see it; declarations it alone refers to aren't
    shown either.
  - The station recipe now reads `config.Get("stations").AV()`, the
    simpler path 2026-0009's read noted, rather than leaving it for
    2026-0010, as the recipe was being rewritten anyway.
  - "Compared with plain Go" lost its hand-written code, which nothing
    ran, and points at the twins instead.
  - `doc.Examples` names a package-level example `_name`, keeping its
    suffix out of `Suffix`; the planted case caught the first draft
    keying outputs by `Suffix`, which made every twin agree.
  - The rules in `CLAUDE.md` and the README's list of documents say how
    the guide is made now.
  - The guide's PDF left "In plain Go, printing the same:" alone at the
    foot of five pages, its code on the next. `docs/print.css` now keeps
    a paragraph with a code block after it, and a paragraph's lines
    together in twos. Prince 17 ignored `p:has(+ pre)`, and pandoc
    wraps highlighted code in `div.sourceCode`, so the rule names both
    that and `pre`. The examples' PDF grew from 76 pages to 79, as
    each description now stays with its code; the others kept their
    page counts. grammar's `print.css` is the same file, and would gain
    from the same rules.
- **The wash-up before the release found two gaps** in `TestHowTo`,
  each reproduced with a planted case before it was fixed. An example
  with no `// Output:` is compiled by `go test` but never run, and the
  generator still put it in the guide as tested, with an empty "It
  prints" and a twin that needn't have printed the same; it's now a
  problem, for either twin. And a plain Go twin with no recipe of its
  own went unreported; it's now named. `TestHowToCatches` plants both.
  No recipe in the guide had either fault.
- **What's left:** the general part, splicing an example into Markdown,
  moves to docref when grammar's guide follows (D2, D4). The chapters
  are 2026-0010 and 2026-0011.
